# 후보를 좁히는 순서

1. 요청이 서버에 도달했는지, Controller에 들어갔는지, SQL/뷰까지 갔는지 구분한다.
2. 예외 체인의 root/cause/suppressed를 구분한다. 가장 깊은 예외가 소스 수정 위치라는 보장은 없다. 생략 프레임은 상위 스택을 참조하고 Native Method/Unknown Source는 위치 미확정으로 둔다.
3. 프로젝트 프레임의 클래스와 실제 패키지를 맞춘다. 같은 파일명이 여러 모듈에 있으면 모두 후보이며 라인이 같아도 확정하지 않는다. 소스 리비전과 배포본이 다르면 로그 라인을 그대로 믿지 않는다.
4. URL·sqlId·메서드로 인덱스를 질의하고 인터셉터·공유 SQL·뷰 설정을 원문으로 확인한다. 미수집 구간을 연결됐다고 가정하지 않는다.
5. 후보마다 관측 사실, 반증 조건, 확인할 파일:라인을 남긴다. 입력→분기→잘못된 값→실패의 인과관계를 확인한다.
6. 예외 없는 페이지 누락은 총건수·pageSize·offset/endRow·ORDER BY·마지막 페이지 경계를 비교한다. 0/1/10/11/20/21건처럼 경계 입력으로 확인한다.
7. 재현 불가라면 확정 가능한 범위와 외부 조건을 분리한다. 사용자에게 필요한 최소 설정·마스킹된 로그·읽기 쿼리를 제시한다.

단순히 오류 문자열이 레퍼런스와 같다는 이유로 CONFIRMED를 붙이지 않는다. 검토 파일에 소거한 후보와 남은 후보를 각각 남긴다.
