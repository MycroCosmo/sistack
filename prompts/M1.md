# M1 — 공통 인덱서

`AGENTS.md`의 규칙을 따른다. 선행 조건: M0 완료 기준 충족.

## 목표

**SI 코드에서 grep이 멈추는 연결을 이어주는 인덱서**를 만든다. 네 스킬(si-trace, si-debug, si-unit-test, si-docs)이 모두 이 결과를 쓴다. 이 인덱서의 정확도가 SIStack의 핵심 가치다.

일반 심볼 검색으로 찾을 수 있는 Java 메서드 호출보다, 문자열·설정으로 이어지는 연결이 우선이다.

## 작업

### 1. 인덱스 스키마

`schemas/index.schema.json`을 먼저 설계한다. 최소한:

- `meta`: 대상 경로, `source_revision`(git 해시, 없으면 null), 생성 시각, 인덱서 버전, 처리 파일 수, 소요 시간
- `nodes`: 화면(JSP), JS 함수, URL 엔드포인트, Controller 메서드, Service/DAO 메서드, SQL 문(`namespace.id`), SQL 조각, 테이블·뷰·프로시저. 각 노드에 `파일:라인`
- `edges`: `from`, `to`, `kind`(calls, requests, maps_to, executes, includes, reads, writes), `status`(CONFIRMED/LIKELY/UNRESOLVED), `evidence`(`파일:라인`), `reason`(LIKELY/UNRESOLVED일 때 필수)
- `unresolved`: 확정 못 한 지점 목록과 이유
- `skipped`: 처리 못 한 파일·패턴

### 2. 수집기 (`lib/indexer/`)

수집기를 계층별 모듈로 나눈다. 각 모듈은 단위 테스트를 가진다.

| 모듈 | 수집 내용 |
|---|---|
| `jsp` | form action, `<c:url>`, `<a href>`, 인라인 스크립트의 요청 URL, 포함된 JS 파일 |
| `js` | `$.ajax`, `$.post`, `$.get`, `location.href`, `fetch`, `form.submit()`의 URL. 문자열 조합 URL은 UNRESOLVED (상수 부분만 기록) |
| `spring` | `@Controller`/`@RestController`, `@RequestMapping` 계열(클래스 경로 결합, 배열 값, method 속성), XML의 핸들러 매핑, 인터셉터 매핑 경로 |
| `java` | 필드·생성자·setter 주입 타입, 그 필드에 대한 메서드 호출, `SqlSessionTemplate`/`SqlMapClient` 호출의 sqlId 문자열 |
| `mybatis` | Mapper XML `namespace.id`, `<include refid>`, `resultMap`, `${}` 사용 위치, Mapper 인터페이스 ↔ XML 연결 |
| `ibatis` | iBatis 2 `sqlMap` namespace·id, `<include>` |
| `sql` | SQL 본문에서 테이블·뷰·프로시저 참조 (FROM, JOIN, INSERT INTO, UPDATE, DELETE FROM, MERGE, CALL). 읽기/쓰기 구분 |

규칙:
- **문자열 검색 결과만으로 CONFIRMED를 붙이지 않는다.** 선언과 사용이 구조적으로 이어질 때만 CONFIRMED.
- 주석 안의 코드는 무시한다 (Java `//`, `/* */`, JSP `<%-- --%>`, HTML `<!-- -->`, XML 주석, JS 주석).
- 같은 이름 메서드가 여러 클래스에 있으면 주입 타입으로 구분하고, 구분 못 하면 LIKELY + 후보 목록.
- 인터페이스 → 구현체가 여러 개면 LIKELY + 후보 목록.
- 파싱 실패는 전체를 멈추지 말고 `skipped`에 기록하고 계속한다.

Java 파싱 방식(정규식 기반 vs 파서 라이브러리)은 직접 판단한다. 라이브러리를 쓰면 라이선스·크기·Java 버전 지원 범위를 `docs/decisions.md`에 기록한다. 둘 다 시도해 비교할 필요는 없다.

### 3. CLI

```bash
node scripts/build-index.mjs <대상경로> [--out .sistack/index/index.json] [--summary]
node scripts/query-index.mjs <index.json> --from <JSP|URL|클래스#메서드|namespace.id> [--depth N]
node scripts/query-index.mjs <index.json> --to <테이블|namespace.id|클래스#메서드>
```

- `--summary`는 사람이 읽을 요약(노드·엣지 수, 상태별 개수, skipped 상위 패턴)을 출력
- `query-index`의 `--from`은 정방향(화면 → 테이블), `--to`는 역방향(테이블 → 화면). 스킬이 이 두 방향을 쓴다
- 출력은 JSON 기본, `--format text` 옵션 제공

### 4. legacy-board 검증

- `evals/legacy-board-traps.md`의 함정을 하나씩 단위 테스트로 만든다. 각 함정이 기대 상태로 분류되는지 확인한다.
- 함정이 아닌 정상 흐름도 CONFIRMED로 이어지는지 확인한다 (과도한 UNRESOLVED도 실패다).

### 5. eGovFrame 실행

- `scripts/fetch-testbed.mjs egovframe`로 받은 코드 전체를 인덱싱한다.
- 끝까지 도는지, 소요 시간, 노드·엣지 수, 상태별 비율, `skipped` 상위 패턴을 기록한다.
- 처리 못 한 패턴은 `docs/limitations.md`에 기록한다. 고칠 수 있는 것은 고치고, 못 고치면 이유를 적는다.

### 6. 정답 초안 작성

정답은 **인덱서 출력을 복사해서 만들지 않는다.** 소스를 직접 읽어 작성한다. 인덱서 결과를 정답으로 쓰면 자기채점이 된다.

- eGovFrame에서 **서로 다른 패턴의 메뉴 3개**를 고른다. 선정 기준: 하나는 단순 CRUD, 하나는 공통 모듈(페이징·공통코드 등)을 거치는 것, 하나는 Mapper/DAO 방식이 다르거나 iBatis 등 다른 구조. 고른 이유를 적는다.
- legacy-board에서 흐름 2개 (게시판 목록 검색, 게시글 등록).
- 각 흐름을 `evals/trace/<id>/expected.draft.json`과 사람이 읽기 쉬운 `expected.draft.md`로 작성. 모든 연결에 `파일:라인`.

### 7. eval 스크립트

`scripts/eval-index.mjs`: 승인된 `expected.json`과 인덱서 결과를 비교해 연결 단위로 누락(false negative)·과탐(false positive)·상태 불일치를 출력한다. 이 단계에서는 `expected.draft.*`만 있으므로 스크립트가 draft로 동작하는지만 확인한다.

## [GATE] 정답 초안 검토

정답 초안 5건을 작성한 뒤 **멈추고 보고한다.** 보고에는 다음을 포함한다.

- 정답 초안 파일 경로 5개
- 메뉴 선정 이유
- 초안을 쓰면서 애매했던 연결 (사용자 판단이 필요한 것)
- 인덱서 현재 결과와 초안의 차이 미리보기 (참고용, 정답 판정 아님)

사용자가 승인하면 `expected.draft.*` → `expected.*`로 이름을 바꾸고 다음으로 진행한다.
