## SI에 맞게 바꿀 점

pstack bug-fix는 "먼저 재현"이 전제다. SI에서는 운영·개발 서버 로그만 있고 로컬 재현이 안 되는 경우가 많다. 그래서:

- **로그·스택트레이스 분석을 기본 경로**로 둔다. 재현은 가능할 때만 한다.
- 재현하지 못했으면 원인 판단에 도달한 증거 단계를 표시하고 "미재현"을 명시한다.
- 수정은 기본적으로 **제안까지**만 한다. 사용자가 수정을 요청하면 pstack tdd처럼 실패하는 테스트를 먼저 쓰고 고친다.
- 로그에는 개인정보가 섞여 있다고 가정하고, 분석 전에 `lib/mask`로 마스킹한다. 보고서에 원본 로그를 그대로 옮기지 않는다.

## 스킬 구성

```text
skills/si-debug/
├── SKILL.md
├── references/
│   ├── triage.md              # 증상 → 원인 후보 분류 절차
│   ├── patterns-spring.md     # 매핑 404/405, 바인딩, 인터셉터, 트랜잭션
│   ├── patterns-mybatis.md    # BindingException, TooManyResults, ${} 오류, 타입 핸들러
│   ├── patterns-db.md         # ORA-/PostgreSQL/Tibero 에러 코드별 원인
│   ├── patterns-web.md        # 한글 깨짐, 세션 만료, JSP 컴파일 오류, jQuery 요청 오류
│   └── was-logs.md            # Tomcat/JEUS/WebLogic 로그 위치·형식 차이
└── scripts/
    ├── parse-trace.mjs        # 스택트레이스에서 예외 체인·프로젝트 프레임 추출
    └── lib/
```

`patterns-*.md`는 "흔한 원인 목록"이 아니라 **증상 → 확인할 위치 → 확정하는 방법** 형식으로 쓴다.

## SKILL.md 요구사항

**description 예시:** "에러 로그, 스택트레이스, '저장하면 오류 나요' 같은 증상에서 근본 원인을 찾고 근거와 수정안을 제시한다. ORA- 에러, MyBatis 오류, 404, 한글 깨짐, 화면이 안 뜨는 문제 등 SI 프로젝트 오류 분석에 사용."

**절차**
1. **입력 정리** — 로그·스택트레이스 마스킹, `parse-trace`로 예외 체인과 프로젝트 코드 프레임 추출. 증상만 있으면 증상을 재현 조건(화면, 입력값, 사용자 권한) 형태로 정리.
2. **위치 특정** — 인덱스로 해당 프레임·URL·sqlId의 흐름을 잡는다 (si-trace를 부르지 않고 인덱서를 직접 쓴다. 단독 설치 동작 보장).
3. **원인 후보** — `references/patterns-*`로 후보를 만들되, 후보마다 확인할 위치를 정한다.
4. **확정** — 후보를 하나씩 소스·설정·SQL로 확인해 소거한다. 가장 깊은 원인까지 "왜"를 따라간다. 증상만 막는 null 체크·try-catch는 원인 수정이 아니다.
5. **증명** — 가능하면 원인을 드러내는 테스트나 스크립트를 `.sistack/runs/<run-id>/evidence/`에 작성해 실행한다. 불가능하면 멈춘 단계와 이유를 적는다.
6. **수정안** — diff 형태로 제안. 같은 원인이 다른 곳에도 있는지 인덱스로 확인해 함께 적는다.

**출력**
- **증상 요약**
- **원인** — 한 문장 + `파일:라인` + 증거 단계 + 재현 여부
- **원인까지의 경로** — 어떻게 좁혔는지 (소거한 후보 포함)
- **수정안** — diff, 같은 패턴의 다른 위치
- **확인 방법** — 수정 후 확인할 테스트·절차
- **확정 못 한 것** — 추가로 필요한 정보 (특정 로그, DB 값, 설정 파일 등)

**금지**
- 근거 없이 원인을 단정하지 않는다. 후보가 여러 개 남으면 그대로 보고한다.
- 사용자 요청 없이 소스를 수정하지 않는다.
- 운영·개발 DB에 접속하지 않는다. 필요한 DB 값은 사용자에게 확인할 쿼리를 제시한다.
- 마스킹하지 않은 로그를 출력하지 않는다.

## 버그 케이스 (eval)

`evals/debug/cases/<id>/`에 다음 구조로 7건을 만든다.

```text
<id>/
├── bug.patch          # legacy-board에 적용하는 패치
├── symptom.md         # 사용자가 말할 법한 증상 설명
├── symptom.log        # 증상 로그 (가짜 개인정보 포함 → 마스킹 테스트 겸용)
└── expected.draft.md  # 원인 위치, 원인 설명, 기대 증거 단계
```

케이스 (각각 다른 패턴):
1. MyBatis 파라미터 바인딩 오류 (`@Param` 누락 등)
2. JS 요청 URL과 Controller 매핑 불일치로 404
3. 한글 깨짐 (인코딩 설정 누락·순서 문제)
4. 인터셉터를 우회하는 경로에서 세션 값 NPE
5. 공통 페이징 경계 오류로 마지막 페이지 데이터 누락 (**예외 없는 오동작**)
6. `${}` 정렬 파라미터로 특정 입력에서 SQL 오류
7. Oracle 에러 코드가 담긴 로그만 있고 로컬 재현 불가 (**재현 불가 케이스**, 근거 없이 단정하지 않는지 확인)

`scripts/eval-debug.mjs`: 케이스마다 legacy-board 임시 복사본에 패치를 적용하고, 스킬 결과의 원인 위치를 정답과 비교한다. 원본 legacy-board는 건드리지 않는다.

## [GATE] 정답 승인 + 실제 사례

버그 케이스 7건과 정답 초안을 만든 뒤 **멈추고 보고한다.** 사용자는:

1. 정답 초안을 검토·승인한다.
2. `evals/private/`에 마스킹한 실제 업무 에러 사례 2~3건을 넣는다 (같은 구조, 패치 대신 관련 소스 발췌).

승인 후 7건 + 실제 사례로 eval을 돌린다. 실제 사례 결과는 보고서에 **위치·적중 여부만** 쓰고 내용은 인용하지 않는다.
