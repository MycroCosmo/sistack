# M2.5 — Thymeleaf 수집기

`AGENTS.md`를 따른다. 선행 조건: M2 완료, legacy-board 검색·등록 승인 정답 존재, 인증 Helper 누락 보정 후 학습 5건 eval 확인.
시작할 때 `git status`와 `MILESTONES.md`의 완료 근거를 확인한다. 이 프롬프트는 사용자가 실행을 지시할 때 수행한다. 문서 작성 요청만으로 구현을 시작하지 않는다.

## 목표와 범위

Ian의 JSP → Thymeleaf 이관에서 to-be 화면의 요청을 Controller → Service → Mapper → SQL·테이블까지 추적한다. 공통 인덱서와 기존 si-trace를 확장하며 새 제품 스킬을 만들지 않는다.

- 테스트베드: `examples/legacy-board-thymeleaf/`.
- 학습: 기존 `legacy-board-search`, `legacy-board-create` 승인 정답과 대응하는 Thymeleaf 검색·등록 2건.
- held-out: 자체 테스트베드의 Thymeleaf 삭제 AJAX 1건 + 외부 공개 Thymeleaf 프로젝트의 화면 → Controller 흐름 1건. 서로 다른 case-id로 등록·채점하고 학습과도 분리한다.
- 외부 테스트베드: Spring PetClinic을 우선 선택하고 공식 저장소의 고정 커밋을 `.testbeds/spring-petclinic/`에 클론한다. 소스는 커밋하지 않는다. JPA 등 Controller 이후 서버 흐름은 외부 held-out 범위 밖이다.
- JPA 수집기(Repository 메서드명, `@Query`, `@Entity`/`@Table`)와 Vue3+REST 수집기(`.vue`, axios, router, `application.yml`)는 v0.2 백로그로만 유지한다.

## 1. [GATE] 의존성 추가 승인

추가하기 전에 `docs/m2.5-dependency-proposal.md`에 다음을 구체적으로 작성하고 **멈춘다**.

- `org.thymeleaf:thymeleaf-spring5`의 정확한 버전과 Java 8·기존 Spring 5/javax 호환 근거
- `nz.net.ultraq.thymeleaf:thymeleaf-layout-dialect`의 Java 8 호환 버전·라이선스와 Groovy 등을 포함한 전이 의존성
- 직접·전이 의존성, 라이선스, 추가 이유, 영향받을 pom·MVC 설정과 예상 diff
- JSP·Thymeleaf 공존 설정안: 각 리졸버의 order·viewNames와 템플릿 prefix/suffix, 공통코드 목록 JSP 유지
- 기존 승인 의존성 재사용 범위, 실행·검증 방법

공식 문서·배포 메타데이터를 확인해 버전을 선택한다. Java 8 호환성을 가정하지 않는다. 사용자 승인 전 pom에 추가하거나 의존성 설치·설정 변경을 진행하지 않는다. 승인 결과와 이유는 `docs/decisions.md`에 기록한다.

## 2. 테스트베드와 학습 정답

승인 후 기존 legacy-board를 기준으로 새 테스트베드를 만든다.

- Controller·Service·구현체·Mapper/DAO·SQL과 URL·HTTP 메서드·모델 계약을 유지한다. 서버 파일의 상대 경로별 내용/해시를 비교해 동등성을 확인한다.
- 공통코드 목록 `code/list` 1개 화면은 JSP와 필요한 JSP 조각을 유지하고 나머지 화면을 Thymeleaf로 변환한다. JSP·Thymeleaf 뷰 리졸버를 함께 설정하며 Controller 반환 뷰 이름은 유지한다. 뷰 리졸버·템플릿 엔진과 필요한 화면 설정만 변경하고 차이를 기록한다. 서버 계약 변경이 필요하면 조용히 수정하지 말고 별도 승인 대상으로 남긴다.
- Thymeleaf 공통 레이아웃은 Layout Dialect의 `layout:decorate` / `layout:fragment`로 구성한다. 기존 `th:replace`/`th:insert`/`th:include` 프래그먼트 수집 범위도 유지한다.
- Thymeleaf 화면 1개 이상에서 `th:data-*="@{...}"`, `th:attr="data-url=@{...}"`의 두 표기를 사용하고 외부 JS가 요소의 `.data('url')` 등을 읽어 AJAX를 호출하게 한다. 예를 들어 게시판 목록에서 기존 공통코드 JSON endpoint를 호출한다. 삭제 held-out을 학습 검증용으로 소비하지 않는다.
- 로컬 H2·세션·역할·CSRF·jQuery 동작을 유지한다. 기존 legacy-board 원본, 승인 정답, 과거 평가 기록을 덮어쓰지 않는다. 테스트베드에 정답 힌트를 넣지 않는다.
- 검색·등록의 기존 승인 서버 연결을 그대로 대응시키고 화면 근거만 새 소스에서 작성한다. 새 파일·라인·source_files 해시를 가진 `expected.draft.json`/`expected.draft.md` 2건을 별도 사례 디렉터리에 둔다. 자동 수집 결과를 정답으로 복사하지 않는다.

**[GATE] 학습 정답 2건:** 원본과 새 정답의 화면 차이·서버 연결 대응표를 제시하고 멈춘다. 기존 JSP 정답 승인을 새 템플릿 근거의 승인으로 간주하지 않는다. 사용자 승인 후에만 승인본 확정과 학습 채점을 진행한다.

## 3. 수집기 구현과 학습 검증

기존 그래프 계약·근거·마스킹을 재사용하고 외부 Node 의존성을 추가하지 않는다. Thymeleaf 템플릿과 이를 포함하는 화면의 문맥을 함께 확인한다.

| 대상 | 수집·판단 기준 |
|---|---|
| `th:action` | 실제 form의 method·action·submit 관계로 endpoint에 연결한다. 기본 HTML action과 Thymeleaf action을 중복 요청으로 세지 않는다. |
| `th:href`, `th:src`의 `@{...}` | 리터럴 경로, 경로 변수와 쿼리 파라미터를 분리한다. `/board/{id}(id=${row.id})`는 URL 패턴과 Controller 매핑 근거로 판단하며 런타임 id를 지어내지 않는다. 쿼리가 있어도 경로 매칭을 보존한다. |
| `th:replace`, `th:insert`, `th:include` | 실제 템플릿·`th:fragment` 선언과 참조를 연결하고 프래그먼트 안 요청도 따라간다. 매개변수, 상대 경로, 중첩·순환 참조를 처리하거나 한계로 명시한다. |
| `th:inline="javascript"`의 AJAX URL | 인라인 식(예: `/*[[@{/board/delete.do}]]*/`)과 실제 AJAX 소비 위치·HTTP 메서드를 함께 확인한다. 자연 템플릿의 fallback 리터럴을 별도 실제 요청으로 중복 처리하지 않는다. |
| `layout:decorate`, `layout:fragment` | Layout Dialect 등록 설정, 레이아웃 경로, 본문과 레이아웃의 같은 이름 fragment를 근거로 연결한다. 동적 레이아웃·중복 fragment·상속/순환 경계는 이유와 함께 미확정으로 남긴다. |
| `th:data-*`, `th:attr`의 data URL → 외부 JS AJAX | URL을 가진 실제 요소와 속성명, 외부 JS 포함 관계, 선택자·이벤트 대상, `$(el).data('url')`/`.attr('data-url')`/`dataset.url` 소비와 AJAX 메서드를 함께 추적한다. 미사용 data URL 선언을 요청으로 세지 않고 다른 요소·공유 JS의 값을 섞지 않는다. |
| Controller 반환 뷰 → JSP/Thymeleaf | 실제 리졸버 등록·order·viewNames, 템플릿 리졸버의 prefix/suffix와 대상 파일을 따라 판정한다. 설정으로 유일하게 결정된 경우만 CONFIRMED, 순서·조건·사용자 정의 리졸버 때문에 판정 불가면 후보와 이유를 남겨 LIKELY로 둔다. `redirect:`/`forward:`·JSON 응답을 템플릿으로 잘못 연결하지 않는다. |

- 정적 리소스·외부 링크·`#`와 서버 endpoint 요청을 구분한다. 단순 문자열 발견만으로 CONFIRMED를 주지 않는다.
- 동적 템플릿명·동적 URL 베이스·모호한 매핑은 LIKELY/UNRESOLVED와 이유를 남긴다. Thymeleaf 식을 실행하거나 임의 값을 대입하지 않는다.
- 고정 URL만 성공하는 테스트에 그치지 않는다. 경로 변수·복수 쿼리·프래그먼트 3종·인라인 AJAX·레이아웃/본문·두 data URL 표기와 외부 JS 소비·리졸버 공존/모호성·동적 미확정·리소스 오탐을 합성 사례로 검증한다. held-out 2건은 이 단계의 튜닝·회귀 테스트에 사용하지 않는다.
- 뷰 반환 연결은 기존 그래프 계약을 확인해 관계·스키마·eval 범위를 명시하고 검증한다. 기존 JSP 학습 정답의 서버 scope를 새 뷰 연결 때문에 자동 확대하지 않는다. 신규 학습 정답에는 설정에 따른 뷰 선택과 data AJAX의 추가 화면 연결을 별도 범위로 명시해 승인받는다.
- 학습 2건은 화면 노드 대응을 분리한 뒤 endpoint부터 서버의 `from/to/kind/status`와 연결 수를 비교한다. 파일 루트·해시 ID 차이만 정규화하고 서버 연결의 추가·누락·상태 차이를 숨기지 않는다.
- 기존 JSP 학습 5건도 회귀 채점한다. 보정된 56개 승인 연결을 기준으로 누락·과탐·상태 불일치를 보고하며 새 학습과 합산해 일반화 점수로 쓰지 않는다.
- `skills/si-trace/references/`의 기술별 안내, `docs/limitations.md`, 필요 시 활성화 설명을 갱신하고 `scripts/sync-shared.mjs`로 단독 설치 복사본을 동기화한다.

## 4. [GATE] held-out 2건 정답과 구현 동결

학습 구현·검증을 마친 뒤 **두 held-out의 흐름 탐색·정답 초안 작성에 착수하기 전에 구현 revision과 도구 파일 해시를 동결**한다. 소스만 읽어 별도 사례별 `expected.draft.json`/`expected.draft.md` 총 2건을 작성하고 **멈춘다**.

- 삭제 AJAX 정답에는 화면 이벤트·인라인 URL·endpoint·Controller·Service·Mapper·SQL·테이블의 근거와 범위를 명시한다. 승인된 범위 밖 항목은 보충 주장으로 분리한다.
- 외부 사례는 공식 저장소 URL·고정 SHA·라이선스·기술 버전을 기록한 뒤 `.testbeds/spring-petclinic/`에 클론하고 origin·HEAD·작업 트리를 확인한다. 기존 폴더는 리셋·덮어쓰기하지 않는다. `.testbeds/`의 gitignore와 `git ls-files`로 소스가 추적되지 않음을 검증한다. 재수집 수단도 revision 고정과 기존 작업 보존을 지킨다.
- 외부 정답은 화면 → 요청 URL/HTTP 메서드 → Controller 매핑까지 1건이다. JPA Repository·Entity·쿼리·DB 구간은 평가와 구현 모두 범위 밖이다. 원문 코드 복사 없이 파일:라인·해시·승인 정답·평가 결과만 저장소에 기록한다. 외부 프로젝트의 Java 버전은 pom에서 판정하며 로컬 테스트베드의 Java 8 조건을 강제로 적용하지 않는다.
- 정답 승인 전 구현 수정·held-out 채점·사례 대응 튜닝을 금지한다. 학습 검증을 명분으로 동결을 풀지 않는다.
- 두 정답 승인 후 같은 동결 구현으로 각각 첫 실행한다. 한 사례의 결과를 보고 다른 사례 첫 실행 전에 구현을 수정하지 않는다. 구현 지문이 달라졌다면 첫 점수로 제출하지 말고 차이를 보고한다.
- 새 run-id에 원본 인덱스·trace·검토·manifest·보고서·eval·정답/도구/소스 해시를 보존한다. 누락·과탐·상태 불일치를 각각 보고하며 실패도 그대로 남긴다.
- **[GATE] 수정 전 첫 점수 보고:** 두 사례를 개별 등록·채점해 각각의 첫 결과와 원본을 보존하고 멈춘다. 학습이나 서로 다른 평가 범위를 합쳐 단일 정확도로 표현하지 않는다. 사용자 지시 후에만 후속 수정을 진행하며 새 run-id에 기록한다. 수정 후 점수는 일반화 성능이 아니다.
