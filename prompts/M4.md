# M4 — si-unit-test (← pstack tdd, test-behavior-not-implementation)

`AGENTS.md`의 규칙을 따른다. 선행 조건: M1, M3 완료 기준 충족 (M3의 버그 패치를 검증에 쓴다).

## 목표

테스트가 거의 없는 레거시 Java 프로젝트에 **실제로 버그를 잡는 단위 테스트**를 작성하고 실행하는 스킬을 만든다. 결과는 M5 산출물(단위테스트 결과서)의 입력이 된다.

## 2026-10-28 사용자 승인 범위

- 대상은 `examples/legacy-board`와 `examples/legacy-board-thymeleaf` 모두다. 기존 **JUnit 4 + Mockito 4 + spring-test + H2(test 스코프)**만 사용한다. JUnit 5 등 새 의존성을 도입하지 않는다. pom 변경이 필요하면 변경 이유를 보고하고 승인 전 멈춘다.
- M3 학습 10건과 이미 관찰한 held-out 3건은 M4에서 모두 **학습 평가**다. 각각 서비스/매퍼/유틸처럼 테스트 가능한 종류인지, 템플릿·설정·JS 등 범위 밖인지 먼저 분류·기록한다. 패치는 사례별 임시 복사본에만 적용해 생성 테스트를 실행하고, 탐지 가능한 사례를 분모로 탐지 수를 보고한다. 전체 13건의 실행·제외·BLOCKED도 빠짐없이 기록한다. 로그 전용 사례는 실행 가능한 패치가 없음을 명시하며 탐지 성공으로 세지 않는다. 템플릿·JS 결함을 잡기 위한 소스 문자열 검사를 단위 테스트로 만들지 않는다.
- 버그를 잡은 테스트가 있는 사례에서는 **보존된 si-debug v5 제안 diff**를 결함 사본에 적용하고 같은 테스트가 통과하는지 검증한다. **M3 heldout-02(EQUIVALENT)를 반드시 포함**해 사람의 동등 수정 판정을 동작 근거로 보강한다. 첫/v5 원본과 점수, 제안 diff는 바꾸지 않는다.
- 반환값·호출을 망가뜨린 임시 변이에서도 통과하는 약한 테스트(단언 없음, 목 호출만 확인 등)를 고치거나 제거하고 사례 1개 이상을 실제 실행 기록으로 남긴다.
- 학습 평가를 마친 후 구현·생성 테스트·평가 도구를 동결하고 **[GATE]에서 멈춘다**. 동결 후 Claude가 `evals/private/`에 새 버그 패치 3건을 제공한다. 새 패치 내용은 읽지 않고 동결된 생성 테스트를 실행해 탐지 여부만 첫 점수로 보존한다. 사례별 튜닝·동결 후 테스트 변경 금지. 새 held-out 결과는 학습 13건과 합산하지 않는다.
- `test-results.json`은 M5 단위테스트 결과서 입력 계약이다. 테스트 표시 이름은 **한국어 업무 표현**으로 기록하고 스키마로 검사한다. 실행 환경·대상 클래스/메서드·실패 마스킹·revision·출처를 함께 기록한다.
- 이 조건을 먼저 프롬프트에 반영·커밋한 후 구현한다. 새 held-out 출제나 외부 서비스 요청을 대신 수행하지 않는다.

## SI에 맞게 바꿀 점

- **환경을 먼저 탐지한다.** Java 버전, JUnit 4/5, Mockito 유무와 버전, Spring 버전, 빌드 도구. 프로젝트에 있는 것만 쓴다.
- **의존성 추가는 승인 사항이다.** `pom.xml`/`build.gradle` 변경이 필요하면 무엇을 왜 추가하는지 제시하고 멈춘다. SI에서 빌드 파일 변경은 형상관리 대상이다.
- **DB 의존 코드**: Service는 Mapper/DAO를 목으로 대체한 단위 테스트가 기본이다. Mapper SQL 테스트는 프로젝트에 테스트 DB 설정이 이미 있을 때만 쓴다. 운영·개발 DB 연결 설정을 테스트에 쓰지 않는다.
- **기존 코드를 테스트하기 쉽게 고치지 않는다.** 테스트를 위해 운영 코드를 바꿔야 하면 변경안을 제시하고 멈춘다 (SI에서 기능 코드 변경은 별도 승인 대상).
- **테스트 이름은 한국어 업무 표현**으로 읽히게 쓴다 (JUnit 5는 `@DisplayName`, JUnit 4는 메서드명 규칙을 프로젝트 관례에 맞춤). 단위테스트 결과서에 그대로 들어가기 때문이다.

## SKILL.md 요구사항

**description 예시:** "레거시 Java/Spring 프로젝트의 Service·유틸 클래스에 JUnit 단위 테스트를 작성하고 실행한다. '이 서비스 테스트 코드 짜 줘', '단위 테스트 만들어 줘', '이 버그 회귀 테스트 추가해 줘' 같은 요청에 사용. 테스트 결과는 단위테스트 결과서 작성에 쓸 수 있는 형식으로 저장한다."

**절차**
1. **환경 탐지** — `detect-env`. 테스트를 돌릴 수 없는 환경이면(빌드 실패, JDK 없음) BLOCKED로 끝내고 필요한 것을 알려준다.
2. **대상 파악** — 인덱스로 대상 메서드의 호출 관계(어떤 Mapper/DAO를 쓰는지)를 확인한다.
3. **케이스 도출** — 정상, 경계값(빈 값, null, 0, 마지막 페이지), 예외, 권한별. 업무 의미로 이름을 붙인다.
4. **작성** — 프로젝트의 기존 테스트 관례(패키지, 이름, 베이스 클래스)를 따른다. 없으면 프로젝트 소스 구조를 따른다.
5. **실행** — `run-tests`. 실패하면 테스트가 틀렸는지 코드가 틀렸는지 구분한다. 테스트가 틀렸으면 고치고, **코드가 틀렸으면 코드를 고치지 말고 결함으로 보고**한다.
6. **약한 테스트 점검** — 검증 대상 메서드의 반환값·호출을 망가뜨렸다고 가정해도 통과할 테스트(단언 없음, 목 호출만 검증, 항상 참인 단언)는 고치거나 삭제한다.
7. **결과 저장** — `test-results.json` + `report.md`

**si-debug 연계:** 입력에 si-debug run이 있으면(`parent_run_ids`), 그 원인을 드러내는 회귀 테스트를 먼저 쓴다. 수정 전에는 실패, 수정 후에는 통과해야 한다.

**금지**
- 단언 없는 테스트, 커버리지 수치만을 위한 테스트
- 사용자 승인 없는 빌드 파일·운영 코드 변경
- 운영·개발 DB 접속 설정 사용
- 실행하지 않은 테스트를 통과로 기록

## 검증

1. legacy-board와 legacy-board-thymeleaf의 주요 Service(게시판 목록·등록·수정·삭제, 공통 페이징, 공통코드) 및 테스트 가능한 Mapper에 스킬로 테스트를 작성하고 실행한다. 기존 JUnit 4/Mockito 4/spring-test/test H2만 사용한다.
2. **버그 탐지 검증 (학습):** M3 학습 10건 + 기존 held-out 3건을 먼저 분류하고, 각각 패치를 적용한 임시 복사본에서 생성 테스트를 돌린다. 기존 held-out은 이미 관찰했으므로 M4에서는 학습으로 취급한다.
   - 모든 버그를 잡을 필요는 없다 (404, 인코딩, 인터셉터 우회는 단위 테스트 범위 밖일 수 있다). 대신 각 케이스가 단위 테스트로 잡을 수 있는 종류인지 먼저 분류하고, 잡을 수 있는 종류 중 몇 개를 잡았는지 보고한다.
   - 이 수치는 eval 정답이 아니라 테스트 품질 지표다. 표본 크기와 함께 보고한다.
3. `scripts/eval-unit-test.mjs`로 2번을 재실행 가능하게 만든다.
4. 테스트 생성 후 `pom.xml` 변경이 없었는지 확인한다.
5. 탐지한 사례에는 si-debug v5 diff를 적용해 동일 테스트가 통과하는지 확인한다. M3 heldout-02의 EQUIVALENT 수정은 필수다.
6. 약한 테스트 1개 이상에 대해 원래 테스트/결함 변이/보강 테스트의 결과를 기록한다. 운영 원본은 수정하지 않는다.
7. 학습 후 동결·GATE. 이후 별도 지시로 새 패치 3건을 보지 않고 동결 테스트로 실행해 탐지 여부만 첫 결과로 보존한다.

## [GATE] 학습 종료·새 held-out 출제 전 동결

학습 평가와 약한 테스트 보강, v5 수정안 동작 검증을 마치면 동결 리비전·파일 해시·테스트 목록·평가 절차를 기록하고 멈춘다. 새 패치 3건은 동결 후 Claude가 출제하며, 이 GATE 이전에 열람하거나 생성하지 않는다. 사용자 지시 후에도 패치 원문은 에이전트에 출력하지 않고 도구가 임시 사본에 적용해 생성 테스트 탐지 여부만 보존한다. 실패·빌드 오류·환경 BLOCKED를 구별하고 첫 결과를 덮어쓰지 않는다.

## 신규 held-out 첫 결과 이후 사용자 승인 보정 — 2026-10-28

첫 결과 0/3과 원본은 불변이다. 테스트 도출을 정상 소스의 인덱스 기반으로 자동화하고 실패 테스트부터 검증한다. Mapper if/when/otherwise 분기별 입력·실행, UPDATE SET 컬럼별 값 변경 후 재조회, INSERT 전체 명시 컬럼 재조회, Service 비교식/상수의 허용·거부 경계 쌍을 coverage-plan.json으로 남긴다. 보고서에는 계획 대비 실제 생성/실행/통과 충족률과 미해결을 표시한다.

패치를 보지 않고 두 정상 프로젝트에서 다시 생성한 뒤 M3 기존 학습 13건과 M4 첫 held-out 3건을 새 run-id의 v2로 검증한다. v2는 결함 수정 확인이며 일반화 성능이 아니다. 완료 후 새 구현·생성 테스트·계획을 다시 동결하고 멈춘다. 이후 신규 3건은 사용자가 동결 후 별도로 출제한다.
